## 반드시 태어나고, 결국 쇠락한다
인터넷 정신, 참 아름다운 단어다. '정신'이라는 이름을 붙인 모든 단어는 듣는 순간 눈부신 미래, 순수한 이상향이 떠오르는 듯하다. 게다가 인터넷 정신은 표면적인 '정신'이라는 이름에 그치지 않고, 그 '개방, 자유, 협력, 공유'의 핵심과 실천이 인터넷의 황금기를 만들어냈다.

인류 역사상의 사상 해방과 지식 보급 운동과 비교해 보면, 인터넷 정신의 탄생은 놀랍도록 유사하며, 거의 디지털 시대에 역사가 재생된 것이라 할 수 있다. 자유 소프트웨어 운동(Free Software Movement)은 사용자가 소프트웨어를 사용, 복제, 연구, 수정 및 배포할 권리를 가진다는 것을 확산하는 사회 운동으로, 운동의 궁극적 이념은 네트워크 속 모든 사람(컴퓨터 사용자)을 해방하는 데 있다. 수많은 자유인들이 중세 성당을 지은 장인처럼 한 벽돌 한 벽돌씩 인터넷 대厦를 구축했다. 오픈 소스 코드의 '크라우드소싱' 모델은 사상 공유와 생산력 공유를 통일시켰으며, 이는 계몽 운동의 '지식은 힘이며, 힘은 대중에게 돌아가야 한다'는 핵심과 꼭 닮아 있다.

초기 인터넷 발전은 비교적 높은 진입 장벽으로 인해 사용자 대부분이 고학력·고교육 층이었고, 그들은 주관적으로 권위와 전제에 반대하며 중앙화된 권력(대기업)에 조종당하기를 원하지 않았다. 그들은 컴퓨터 분야에서 '기술 무정부주의'를 실현하고자 했으며, 모든 컴퓨터 사용자가 한 점에 집중되는 것이 아니라 자유로운 권리를 누리기를 바랐다.

결국 자유 의식은 생물학적 유전자 다양성의 부산물에 불과하며, 그 본질은 뇌가 원시적 본능을 억제하는 것이다. 생물학적 유전자 다양성의 진화 목표는 생존과 번식이며, 이에 대응하는 것은 생물이 본능적으로 이로움을 취하고 해로움을 피하는 것이다. 인터넷 정신은 필연이자 우연이다. 필연인 것은 발전에 따라 언제나 그것을 신앙하고 추구하는 사람이 있기 때문이고, 우연인 것은 기꺼이 그 대가를 치르려는 사람은 소수에 불과하기 때문이다.

인터넷 정신의 탄생은 인터넷의 활발한 발전을 촉진하여 일반 대중도 컴퓨터를 사용하고 인터넷의 편리함을 누릴 수 있게 했다. 그러나 사실이 증명하듯, 모든 개인이 인터넷 정신의 대가—지연된 만족, 불확실성 감수, 조정 비용 지불—를 감당하도록 요구하는 것은 결국 허상에 불과하다. 상업 자본은 인간 본성 깊숙이 새겨진 나태와 안일함이라는 저층 코드를 따라, 개구리를 미지근한 물에 넣듯 천천히 조려가며, 사탕으로 사용자를 자신들이 그어 놓은 한 뙈기의 땅으로 인도한다.

'개방, 자유, 협력, 공유'의 핵심은 하나하나가 상업의 신경을 건드린다. 의심할 여지 없이, 인터넷 정신은 매 순간 상업 자본의 이익을 훼손한다. 이것은 오이디푸스적인 숙명으로, 그 거대한 상업 플랫폼(Google, Meta)들은 바로 인터넷 정신의 초기 산물이며, 개방된 TCP/IP, 오픈 소스 코드와 글로벌 협력을 이용해 세워졌다. 그러나 그들이 인터넷의 중심으로 성장한 후, 생존과 재무 보고서를 위해 반드시 개방 정신을 배신하고 폐쇄적인 장벽을 만들어야 했다.

나에게는 재미있는 이야기가 하나 더 있다. 작년에 회사 활동으로 어느 구의 인공지능 연구원을 방문한 적이 있다. 활동 마지막의 강연회에서 발표자가 중미 LLM 모델의 격차를 언급하며, 큰 부분의 원인이 중국어 인터넷에 쓰레기가 너무 많고 고품질 훈련 자료가 적기 때문이라며 통탄해했다. 듣고 나니 좀 우습기도 하고 다소 아이러니하기도 했다. "당신들은 인터넷에서 땅을 둘러싸고 돈을 벌 때만 이 인터넷을 좋아할 수는 없다." 옛 중국어 인터넷의 '개방·평등·공유' 풍토를 망친 것은 바로 당신들 같은 상업 회사들이 아닌가? 그중 가장 우스운 예는 바이두가 여러 차례 대규모로 티에바 데이터를 비운 것으로, 근시안적임을 여실히 보여준다. 현실의 사실도 BAT 중 바이두만이 점점 쇠락하고 있음을 증명한다. 그런데 지금 인터넷 발전이 병목에 부딪혔지만 LLM AI가 대규모로 흥기하자, 뻔뻔하게도 중국어 인터넷이 당신들에게 고품질 데이터를 제공하지 못한다고 탓하다니, 이렇게 황당할 데가 없다. 그렇다면 묻고 싶다. 지금 인터넷에 넘쳐나는 쓰레기 데이터는 어떻게 생겨난 것이며, 누가 이렇게 이끌었는가?

> BTW, 발표자는 또 한 가지 틀렸다. 올해 중국 LLM 발전 상황도 증명하듯, 고성능 LLM을 못 만드는 것은 순전히 실력이 없기 때문이며(바이트댄스, 텐센트, 그리고 모모 화웨이 포함—미안하지만 이 회사만은 감히 이름을 직접 부르지 못하겠다), 중국어 인터넷이 어떻든 간에 전혀 관계가 없다.

## RSS의 아름다움은 공유에 있다
RSS(Really Simple Syndication, 간이 콘텐츠 신디케이션)는 Web 1.0 시대에 탄생하여, 사용자가 사이트를 하나하나 방문할 필요 없이 하나의 리더기를 통해 서로 다른 출처의 정보 업데이트를 자유롭게 구독하고 집계할 수 있게 하는 것을 목표로 한다. 비록 극히 간결한 프로토콜 내용만 가지고 있지만, **개방**되고 **평등**하게 콘텐츠를 모든 구독자에게 배포하여 인류의 지식과 인식을 공유·공동 구축하며, "개방으로 인해 자유롭고, 자유가 자유로운 협력을 가져오며, 협력이 마지막에 공유를 낳고, 공유가 다시 개방을 가져온다"는 생생불식하는 인터넷 정신을 완벽하게 구현한다.

그러나 분명히 RSS는 상업 인터넷의 영역 확장에 극단적으로 대립하는 지점에 있다. RSS는 개방적이고 탈중앙화되어 있으며, 사이트를 우회하여 콘텐츠를 직접 가져오고 광고를 동반하지 않는 모델은 상업 회사에 트래픽과 광고 수익을 가져다줄 수 없어 자연스럽게 주변화되었다. 현재도 일부 회사/조직/개인이 유지하는 시스템이 RSS를 통한 콘텐츠 배포를 지원하지만, 더 많은 콘텐츠는 상업 인터넷에 의해 격리되어, 자유로운 콘텐츠 배포를 지원하지 않을 뿐만 아니라 반크롤링으로 데이터를 엄격히 격리한다.

이 블로그는 주로 스스로 배포하고 만물을 자유롭게 배포할 수 있는 RSS 아키텍처 한 세트를 소개하고자 한다. 주로 다음을 포함한다:
- 네이티브로 RSS/Atom 프로토콜을 지원하는 콘텐츠;
- 자유로운 배포를 지원하지 않는 콘텐츠;
- 안전한 자체 배포 아키텍처;

### 콘텐츠를 배포하는 방법
[RSSHub](https://docs.rsshub.app/zh/)는 세계에서 가장 큰 RSS 네트워크라고 자칭하며, 그 목표는 만물皆 RSS다. RSSHub는 해당 라우트를 작성하기만 하면 각 회사의 담장 정원 안의 콘텐츠를 RSS 구독 피드로 변환한 다음, RSS 리더기에 넘겨 열람할 수 있다.

공식 RSSHub를 사용하면 콘텐츠 소속 회사의 반크롤링 정책을 촉발할 수 있으므로, 자체 배포가 비교적 권장되는 방식이다. 공식 배포 문서에 따라, 나는 자체 배포 부담을 최대한 줄이고 성능과 배포 용이성을 높이기 위해 일부를 간소화했다.

개인적으로는 `docker-compose`로 RSShub를 배포하고 `redis` 캐시를 사용하여 사용 경험을 향상시키는 것을 추천하며, 개인 필요에 따라 `browserless/chrome` 배포 여부를 선택하면 된다.

`browserless/chrome`이 없는 `docker-compose.yaml`은 다음과 같다:
```bash
services:
    rsshub:
        image: diygod/rsshub # or ghcr.io/diygod/rsshub
        restart: always
        ports:
            - '1200:1200'
        environment:
            ALLOW_ORIGIN: '*'
            NODE_ENV: production
            CACHE_TYPE: redis
            REDIS_URL: 'redis://redis:6379/'
        healthcheck:
            test: ['CMD', 'curl', '-f', 'http://localhost:1200/healthz']
            interval: 30s
            timeout: 10s
            retries: 3
        depends_on:
            - redis

    redis:
        image: redis:alpine
        restart: always
        volumes:
            - redis-data:/data
        healthcheck:
            test: ['CMD', 'redis-cli', 'ping']
            interval: 30s
            timeout: 10s
            retries: 5
            start_period: 5s

volumes:
    redis-data:

```

`browserless/chrome`이 필요하면 공식에서 제공하는 yaml을 참고하면 되며, 교차 출처를 허용하는 것을 잊지 말자:
```bash
services:
    rsshub:
        # two ways to enable Playwright:
        # * comment out marked lines, then use this image instead: diygod/rsshub:chromium-bundled
        # * (consumes more disk space and memory) leave everything unchanged
        image: diygod/rsshub # or ghcr.io/diygod/rsshub
        restart: always
        ports:
            - '1200:1200'
        environment:
            ALLOW_ORIGIN: '*'
            NODE_ENV: production
            CACHE_TYPE: redis
            REDIS_URL: 'redis://redis:6379/'
            PLAYWRIGHT_WS_ENDPOINT: 'ws://browserless:3000' # marked
        healthcheck:
            test: ['CMD', 'curl', '-f', 'http://localhost:1200/healthz']
            interval: 30s
            timeout: 10s
            retries: 3
        depends_on:
            - redis
            - browserless # marked

    browserless: # marked
        image: browserless/chrome # marked
        restart: always # marked
        ulimits: # marked
            core: # marked
                hard: 0 # marked
                soft: 0 # marked
        healthcheck: # marked
            test: ['CMD', 'curl', '-f', 'http://localhost:3000/pressure'] # marked
            interval: 30s # marked
            timeout: 10s # marked
            retries: 3 # marked

    redis:
        image: redis:alpine
        restart: always
        volumes:
            - redis-data:/data
        healthcheck:
            test: ['CMD', 'redis-cli', 'ping']
            interval: 30s
            timeout: 10s
            retries: 5
            start_period: 5s

volumes:
    redis-data:

```

서버에 `docker`/`podman`이 설치되어 있는지 확인하고, 실행한다:
```bash
# docker
# up
sudo docker-compose up -d
# down
sudo docker-compose down

# podman
# up
podman compose up -d
# down
podman compose down
```

`docker`/`podman`은 자동으로 누락된 이미지를 가져온다. 중국 내에서 이미지를 가져오려면 VPN 또는 미러 사이트가 필요하다. 클라우드 서비스 제공업체가 제공하는 이미지 가속이나 [public-image-mirror](https://github.com/DaoCloud/public-image-mirror)를 사용하는 것을 추천한다.

RSSHub를 설치하면 자체 배포 인스턴스를 통해 콘텐츠 라우팅을 완료할 수 있다. RSS 구독 피드를 생성하는 것은 브라우저에 공식 플러그인 [RSSHub Radar](https://addons.mozilla.org/zh-CN/firefox/addon/rsshub-radar/)를 설치하는 것을 추천한다. 현재 웹페이지 내용을 스캔하고 사용 가능한 라우트를 감지한 다음, 해당 RSS 구독 피드를 생성할 수 있다.
[![RSSHub-Radar.png](https://i.postimg.cc/d11zYfjX/RSSHub-Radar.png)](https://postimg.cc/f3GH7BFj)

개인 인스턴스를 사용하려면 생성된 링크의 도메인을 자체 배포 인스턴스의 주소로 바꿔야 한다. 예를 들어 생성된 RSS 구독 피드: `https://rsshub.app/zhihu/people/activities/61-8-91-53-69` 를 `http://[ip]:1200/zhihu/people/activities/61-8-91-53-69` 로 바꾼다.

### RSS 리더기
> *Miniflux is a minimalist and opinionated feed reader.*

자체 배포 RSS 리더기로는 `miniflux` 사용을 추천한다. 별로 화려한 기능은 없고, *for content for simple*, **Less is more**의 철학 사상을 완벽하게 따른다.

내 서버의 OS는 `Debian`을 사용하며, 패키지 관리자를 통해 직접 설치할 수 있다:
```bash
# add apt source
sudo echo "deb [trusted=yes] https://repo.miniflux.app/apt/ * *" | sudo tee /etc/apt/sources.list.d/miniflux.list > /dev/null

# update apt
sudo apt update

# install miniflux
sudo apt install miniflux
```

`miniflux`는 PostgreSQL(버전 11 이상, mysql이 아닌 pg를 사용하는 것이 좋다)에 의존한다. `miniflux` 설치 시 miniflux.service가 자동으로 생성되며, `systemctl`을 통해 관리할 수 있다. 설정 파일은 `/etc/miniflux.conf`이다.

설치 후 `miniflux`를 설정하고, nginx ssl로 `miniflux` 서비스를 프록시하여 보안을 보장해야 한다. `/etc/miniflux.conf` 설정은 다음과 같으며, 여기서 pg 비밀번호와 도메인을 변경해야 한다:
```conf
# See https://miniflux.app/docs/configuration.html

RUN_MIGRATIONS=1
PORT=18080
DATABASE_URL=user=postgres password=[pwd] dbname=miniflux2 sslmode=disable
BASE_URL=https://[domain]/miniflux
```

`miniflux`에 대한 nginx 프록시 추가:
```conf
location /miniflux/ {
        add_header Content-Security-Policy upgrade-insecure-requests;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_pass http://127.0.0.1:18080/miniflux/;
        proxy_redirect http://127.0.0.1:18080/ /miniflux/;
        proxy_redirect https://$host/ /miniflux/;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
}
```

마지막으로 `miniflux` 관리자 계정을 만든다.
```bash
# 确保pg正常运行，账号密码已配置，数据库miniflux2已建立
# restart miniflux
sudo systemctl restart miniflux

# create admin user
miniflux -create-admin
Enter Username: ****
Enter Password: ****
```

마지막으로 `https://[domain]/miniflux`에 접속하면 `miniflux`를 정상적으로 사용할 수 있다. `miniflux` 내에서 구독 피드(RSS, Atom, RSSHub)를 추가하면 `miniflux`에서 구독한 콘텐츠를 볼 수 있다. 최종 결과 이미지:

[![miniflux-rsshub.png](https://i.postimg.cc/SKTD4xsP/miniflux-rsshub.png)](https://postimg.cc/bGnQH810)

모바일 접속이 필요하면 브라우저 외에도 서드파티 앱을 사용할 수 있으며, 자세한 내용은 [Third-Party Applications](https://miniflux.app/docs/apps.html)를 참고하라.
