말할 것도 없이, Javaer는 정말 비동기를 거의 작성하지 않는다. 얼마 전 업무 단체 채팅방에서 다음과 같은 대화를 보았다:

```
A: 지금 너희 쪽 인터페이스 반환 속도가 대략 얼마 정도야? 여기는 지금 300초 타임아웃으로 설정되어 있는데, 타임아웃이 너무 길면 여기 tomcat 스레드가 꽉 차버려
B: 내 쪽은 최대 100초 정도일 거야
A: 그럼 여기 먼저 100초로 낮추자
```

"먼저 100초로 낮추자"는 그저 머리가 아프다고 머리를 자르는 격이다. 아마도 Javaer가 Spring을 너무 많이 사용하고, Spring의 주류는 동기 MVC를 작성하는 것이며, webflux/vertx/netty 같은 비동기 프레임워크를 사용하는 프로젝트는 드물기 때문에 일부 Javaer의 비동기에 대한 이해와 사용이 매우 떨어지는 결과를 낳은 것 같다.

대화 속 문제는 전형적인 긴 동기 블로킹이 스레드 풀 스레드를 고갈시켜 서비스를 사용할 수 없게 만드는 경우다. 다른 네이티브 비동기 async/await 언어, 예를 들어 js/rust 등으로 바꾼다면 이런 일 때문에 풀 스레드가 고갈되는 사고는 발생하지 않을 것이다. golang조차 go 코루틴 같은 그린 스레드를 사용하면 스케줄링에서 이런 문제가 나타나지 않는다.

그럼 분명 누군가는 이렇게 물을 것이다. java21부터 네이티브로 virtual thread를 지원하는데, 왜 이런 문제가 여전히 발생할까? 물론 수많은 java 프로젝트가 아직도 java8을 사용하고 있기 때문이다😇. 농담이 아니고, java17을 사용하는 프로젝트라면 이미 상당히 현대적인 java 프로젝트에 속한다. 다른 언어 프로젝트(예: go/rust)가 language dk를 업그레이드하는 빈도가 하늘을 나는 수준이라면, java 프로젝트의 jdk 업그레이드 속도는 땅을 파는 수준이라고 할 수 있다.
