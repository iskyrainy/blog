# 2025年11月18日 Cloudflare 故障

## 一个月内的三次重大故障

继10月初 AWS 和 Azure 发生重大服务中断之后，Cloudflare 于11月18日上午11:28遭遇了一次大规模故障。Cloudflare 表示其网络承载了全球互联网请求的相当大一部分流量，这意味着 Twitter、ChatGPT，甚至 Downdetector 等网络监控工具都出现了不同程度的不可用。

![Cloudflare error](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/3ony9XsTIteX8DNEFJDddJ/7da2edd5abca755e9088002a0f5d1758/BLOG-3079_2.png)

Cloudflare 此次事故持续了大约五个小时，工程师发布了详细的事故报告，解释了根本原因和响应过程。<sup>[1]</sup>

对近期三次故障的简要总结：
* **AWS — 2025.10.20**
  并发问题触发了核心 DNS 记录的意外清除，导致依赖系统发生级联故障。
* **Azure — 2025.10.29**
  配置传播问题导致多个区域的边缘节点加载了无效或不完整的配置。
* **Cloudflare — 2025.11.18**
  错误的访问权限导致功能数据包超出处理限制，迅速压垮系统并引发大面积故障。

尽管触发机制各不相同，但这三起事件都暴露了一个问题：微小的疏忽在全球云基础设施中可能被急剧放大。

## 故障的成因是什么？
云服务商的服务不可用通常来自以下几个方面：
1. 物理与基础设施层：硬件故障、数据中心设施问题、网络和运营商问题。
2. 软件与平台层：软件逻辑缺陷、软件安全漏洞。
3. 人为因素：操作失误、权限错误等。

重要的是，这三起事件**并非**由网络攻击或恶意活动引起——原因都是内部的、技术性的和操作性的。


## 我们能从这些事件中学到什么？

尽管 Cloudflare 使用 Rust 语言来确保绝对的数据内存安全，这保证了 Cloudflare 不会像 AWS 那样出现数据竞争故障，但 Cloudflare 仍然遭遇了大规模故障。
> 顺便说一句，别犯傻去争论 Rust 的 unwrap；那完全不是问题的重点。

这三次故障的原因看起来颇为滑稽，事后看来都源于看似简单的逻辑错误——这些错误如此幼稚，仿佛是新手程序员犯下的。是因为这些大型云服务提供商的程序员技术不过关吗？显然不是。

我之前写过一个数据导入程序，每天检查并更新由推送通知生成的数据文件。逻辑非常简单，但我犯了一个极其简单而愚蠢的错误——在导入过程中使用了一个未加锁的全局变量，导致数据竞争条件，而且这个 bug 在运行一年多后才偶然触发。

这确实是一个非常、非常简单的逻辑错误，以至于在确认 bug 后我难以相信这样的缺陷竟然存在。然而，由于测试设计不充分，这个 bug 悄无声息地上线了。

因此：
- 准确分析业务逻辑并消除逻辑错误（包括数据竞争条件、死锁、未处理的边界条件等）至关重要；
- 必须对代码进行严格的单元测试和集成测试；
