> MySQL公式ドキュメントは[MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/preface.html)を参照。

## Part 6 スキーマの設計と管理
### 6.1 より良いデータ型の選択
以下のルールに従ってください：
- 小さい方が良い：小さなデータ型は通常より高速に動作し、キャッシュ/メモリ/ディスクの使用量が少なく、処理に必要なCPU時間も少なくて済みます。ただし、精度を失ったりスピルが発生したりしないように注意してください。
- シンプルな方が良い：シンプルなデータ型は処理に必要なCPU時間が少なくて済みます。`int`が`varchar`より優れ、`timestamp`が`datetime/date`より優れ、`datetime/date`が`varchar`より優れています。
- デフォルトの`NULL`を避ける：`NULL`を格納するカラムはMySQLにとって最適化が難しく、`NULL`はインデックス、インデックス統計、値をより複雑にし、`NULL`を許容するカラムはより多くのストレージスペースを消費します（やや直感に反します）。
- enumで文字列を置換：いくつかのデフォルト値しか持たないフィールドには、`enum`の使用が良い選択です。MySQLの`enum`は整数と文字列として格納されます。デフォルトではMySQLは`enum`をその文字列値ではなく整数値でソートし、`FIELD()`で明示的にソートルールを指定できます。
   ```mysql
   mysql> CREATE TABLE enum_test (
      -> e ENUM('fish', 'apple', 'dog') NOT NULL  
      -> );
   mysql> INSERT INTO enum_test(e) VALUES('fish'), ('dog'), ('apple');
   mysql> SELECT e + 0, e FROM enum_test;
   +-------+-------+
   | e + 0 |     e |
   +-------+-------+
   |     1 |  fish |
   |     3 |   dog |
   |     2 | apple |
   +-------+-------+
   ```

型の情報：
1. 整数（整数型）: `tinyint(8bit)`、`smallint(16bit)`、`mediumint(24bit)`、`int(32bit)`、`bigint(64bit)`。`unsigned`を設定して範囲を拡大できますが、ストレージとパフォーマンスは同じです。
2. 実数（浮動小数点型）: `float`、`double`、`decimal`。`float`と`double`はOSの標準浮動小数点計算を使用します。正確に計算する必要があるデータには、`decimal`を使用して格納してください。
3. 文字列（文字列型）: `varchar`、`char`、`binary`、`varbinary`。MySQLは各エンジンでこれらを異なる方法で実装しています。
   - `varchar`：`char`よりも少ないストレージを使用します。`varchar`は必要なスペースのみを使用します。`varchar`は文字列の長さを格納するために追加で1または2バイト必要です。**しかし最良の戦略は、本当に必要なスペースだけを割り当てることです。**
   - `char`：非常に短い文字列を格納する場合、またはすべての値がほぼ同じ長さである状況に適しています。もう変更されないデータには、`char`はパフォーマンスの面で`varchar`より優れています。
   - `binary`/`varbinary`：バイナリバイトとして格納され、より良いパフォーマンスを持ちます。
4. blob/text（大容量データ）: MySQLはblob/text全体をインデックスに格納せず、インデックスでソートすることもできません。
   - blob: `tinyblob`、`smallblob(blob)`、`mediumblob`、`longblob`。バイナリバイトとして格納され、エンコーディングやソートルールはありません。
   - text: `tinytext`、`smalltext(text)`、`mediumtext`、`longtext`。エンコーディングとソートルール付きの文字列として格納されます。
5. 日付/時刻（日時型）: `datetime`、`timestamp`。
   - `datetime`：8バイト。範囲は西暦1000年から西暦9999年まで、精度はマイクロ秒、タイムゾーンに依存せず、ソート可能です。
   - `timestamp`：4バイト。範囲は西暦1970年1月1日から西暦2038年1月19日まで、デフォルトでnot null、値を指定せずに挿入または更新すると、MySQLは現在時刻の値を設定します。
6. bit（ビット型）: `bit`、`set`。
   - `bit`：最大長は64ビット、MySQLによって文字列型（ASCII）として処理されるため、`bit`型の使用は避けるようにしてください。MySQLは`bit`データを最も近い整数型（1-8b->tinyint）として格納します。
   ```mysql
   mysql> CREATE TABLE bit_test(a bit(8));
   mysql> INSERT INTO bit_test VALUES(b'00111001');
   mysql> SELECT a, a + 0 FROM bit_test;
   +------+-------+
   | a    | a + 0 |
   +------+-------+
   | 9    |    57 |
   +------+-------+
   ```
   - `set`：いくつかのtrue/false値のコレクション。
7. json: パフォーマンスとストレージの両方で通常のSQLフィールドよりも優れているとはテストされていません。

もう一つ注意すべき点は、識別子（主キーまたは主キーの一部、通常は他のテーブルと結合する接続フィールド）として適切な型を選択することです。**ほとんどの状況で、整数が最良の選択です。** 整数は良いパフォーマンスを持ち、自動増加が可能です（*整数のオーバーフローに注意*）。識別子として`enum`や`set`を選ばないでください。可能であれば文字列型を識別子として使用することは避けてください。文字列型は整数と比較してより多くのストレージを消費し、処理が遅いためです。一部のランダム文字列生成アルゴリズム（UUIDなど）に注意してください：ランダムな値はランダムなインデックス状況を引き起こし、`INSERT`と`SELECT`を遅くします。`UUID`を識別子として使用する場合、`-`を削除することを忘れないでください。より良いのは、`UNHEX()`関数を使用してUUID値を16バイトの数値に変換し、それをBINARY(16)カラムに格納することです。値は`HEX()`関数を使用して16進数形式で取得できます。

IPv4などのいくつかの特別なデータについて、MySQLは`INET_ATON()`と`INET_NTOA()`を提供し、IPと符号なし整数の間で値を交換し、ストレージを16バイトから32ビットに削減します。

### 6.2 スキーマの落とし穴
1. フィールドが多すぎる：MySQLはデータを行単位でキャッシュし、その後サーバーがキャッシュを列にデコードします。そのため、列が多いほどコストがかかります。
2. 結合が多すぎる：適切な冗長設計は合理的です。
3. `enum`の過剰使用

## Part 7 高性能インデックス
### 7.1 インデックス
インデックスはサーバー層ではなく、ストレージエンジン層で実装されています。
1. `b-treeインデックス`<sup>[1]</sup>：InnoDBはB+木<sup>[2]</sup>を使用します。B-treeインデックスは完全なキー値とキー値の範囲またはキープレフィックスの検索に適しています。キープレフィックスの検索は最左プレフィックスに基づく検索にのみ利用可能です。
   - 完全なキー値（全値マッチ）：インデックス内のすべての列にマッチします。
   - 最左プレフィックスにマッチ（最左プレフィックス）：index(field1, field2, ...)、field1または(field1, field2)または(field1, field2, ...)の有効な条件。
   - 列プレフィックスにマッチ（列プレフィックス）：カラムの値の先頭のみにマッチします。
   - 範囲値にマッチ（範囲値）
   - 最左プレフィックスにマッチし、列プレフィックスにマッチ：index(field1, field2, ...)、(field1, field2の先頭)の有効な条件。
2. `hashインデックス`：`=`または`<>`でより良いパフォーマンス、範囲クエリではより悪い<sup>[3]</sup>。
適応ハッシュインデックス：*InnoDBがあるインデックス値が非常に頻繁にアクセスされていることを発見すると、元のB-treeインデックスの上に、メモリ内にハッシュインデックスを構築します。これにより、B-treeインデックスもハッシュインデックスのいくつかの利点を持つようになります*。

### 7.2 高性能インデックス戦略
- プレフィックスインデックス：ストレージコストを下げるために、プレフィックスインデックスはフィールドの部分的なプレフィックスのみを格納します。異なるインデックス値とデータテーブル内の総レコード数の比率（選択性<sup>[4]</sup>）は、プレフィックスインデックスのパフォーマンスを示します。比率が1の場合、プレフィックスインデックスのインデックスパフォーマンスはユニークインデックスと同じであり、より短い文字のみを処理する必要があります。
- マルチカラムインデックス：インデックスマージの代わりにマルチカラムインデックスを使用します。通常、選択性の高いフィールドをマルチカラムインデックスの先頭に置くことは良い選択です。
- クラスタ化インデックス：これは独立したインデックスタイプではなく、**データを格納する**方法です。InnoDBは主キー（または不可視インデックス<sup>[5]</sup>）によってのみデータをクラスタ化します。
- カバリングインデックス：インデックスが必要なクエリのすべてのフィールドの値を含む場合、それをカバリングインデックスと呼びます。B-treeインデックスのみがカバリングインデックスに使用できることに注意することが重要です。

以下のような重複インデックスの設計を避けてください：
- (A, B) と (A)
- (A, ID)：セカンダリインデックスは主キーを含むため、IDは無意味です。

決して使用されないインデックスを削除します。`sys`では、`table_io_waits_summary_by_index_usage`ビューでどのインデックスが一度も使用されていないかを知るのは非常に簡単です。

## Part 8 クエリパフォーマンスの最適化
### 8.1 SQLが遅く実行される理由
クエリをタスクとして考えると、それは一連のサブタスクで構成され、各サブタスクは一定の時間を消費します。クエリを最適化したい場合、実際にはそのサブタスクを最適化したいのです。つまり、一部を排除するか、サブタスクの実行回数を減らすか、サブタスクをより速く実行させるかです。

### 8.2 データアクセスの最適化
1. おそらくデータをクエリするが不要な場合：
   - `limit`の合理的な使用
   - `select *`を使用しない
   - 短時間に同じSQLを実行することを避け、結果をキャッシュに設定する
2. おそらくMySQLが余分なレコードをスキャンする場合：**応答時間、スキャン行数、結果行数を考慮する**。
   - カバリングインデックスを使用してスキャンするようにする
   - テーブル構造を変更する
   - 複雑なSQLを書き換える

### 8.3 SQLの書き換え
遅くて複雑なSQLの場合、それをいくつかの小さなSQLタスクに分割することで、より良いパフォーマンスが得られるかもしれません。複雑なSQLは長いトランザクションを作り、サーバーリソースのほとんどを消費し、多くの行またはテーブルをロックします。単純なSQLはその逆で、繰り返し実行されるものについては、その結果をキャッシュに設定できます。

### 8.4 実行の基本
MySQLにクエリリクエストを送信した後：
1. カスタムクライアントがSQLを送信する；
2. サーバーがSQLを解析、前処理、最適化する；
3. MySQLがエンジンAPIを呼び出して最適化されたSQLを実行する；
4. クライアントに結果を返す。
![MySQL workflow](https://i.postimg.cc/Kjp75GZD/My-SQL-workflow.png)

MySQLオプティマイザ：
MySQLオプティマイザ戦略は2つのタイプに分けることができます：静的戦略と動的戦略。静的戦略は「コンパイル時最適化」のようなもので、一度実行すれば常に同じです。動的戦略は「実行時最適化」のようなもので、実行ごとに異なる場合があります。

いくつかの最適化：
- テーブル結合順序の再定義
- 外部結合を内部結合に変換
- 等価置換：常に真であるいくつかの判定と常に真でないいくつかの判定を削除し、定数としてマークできる判定を置き換える
- インデックスとフィールドのデフォルト値による`COUNT()`、`MIN()`、`MAX()`の最適化
...

> オプティマイザより自分が賢いと軽々しく推測しないでください。😂

**MySQLでの結合**：
任意の`join`について、MySQLは最初のテーブルから行をクエリし、次に2番目のテーブルの行をマッチし、すべてのテーブルがチェックされるまで一つずつ繰り返し、SQLで指定された列を返します。
MySQLの結合オプティマイザはより良いパフォーマンスのために結合順序を並べ替えることができ、オプティマイザは各接続順序のパフォーマンスを評価し、どの接続方法を取るかを決定します。結合するテーブルが`optimizer_search_depth`を超えると、オプティマイザは貪欲アルゴリズムによって結合順序を並べ替えます。

### 8.5 オプティマイザの限界
1. `UNION`の限界：時々MySQLは外部から内部に条件を推論できません。例：`(SELECT ...) UNION (SELECT ...) LIMIT 20;` MySQLは2つのSQL結果のすべてを一時テーブルに入れてから20行を選択します。より良いのは、SQLを`(SELECT ... LIMIT 20) UNION (SELECT ... LIMIT 20) LIMIT 20;`に変えることで、これで一時テーブルは40行だけになります。
2. 等価伝播：大きな`IN`条件のリストを渡すと、実行速度が遅くなります。

### 8.6 特定のSQLの最適化
1. `COUNT()` SQL：行をカウントするには`COUNT(*)`を使用します。`SUM(IF(..., 1, 0))`を`COUNT(... or NULL)`で置き換えます。
2. `JOIN` SQL：SQLがインデックスを使用できることを確認します。
3. `LIMIT/OFFSET` SQL：可能な限りインデックス覆いスキャンを使用します。次に必要に応じて一度結合し、結果列を返します。例：`SELECT id, name FROM user ORDER BY age LIMIT 10000, 5;` -> `SELECT id, name FROM user INNER JOIN (SELECT id FROM user ORDER BY age LIMIT 10000, 5) AS t ON user.id = t.id;`。または`LIMIT`を`BETWEEN ... AND ...`に変更して、SQLがインデックスの範囲スキャンを使用できるようにします。または最後のクエリ行番号を記録します。例：`SELECT ... FROM t ORDER BY id DESC LIMIT 20;` -> `SELECT ... FROM t WHERE id < ... ORDER BY id DESC LIMIT 20;`。
4. `UNION` SQL：`WHERE`、`LIMIT`、`ORDER BY`などの句を手動でUNIONの様々なサブクエリに「プッシュダウン」して、オプティマイザがこれらの条件を最大限に活用して最適化できるようにします。サーバーが行を重複排除する必要が本当にない限り、`UNION ALL`を使用することが重要です。
