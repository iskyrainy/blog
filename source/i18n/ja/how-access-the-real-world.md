## パート1 クラスターファイアウォールを知る
方氏はスーパークラスターの管理者である。彼はクラスター内のノードを保護し、外部からの悪意ある攻撃を防御すると主張している。そのため、方氏は巨大で*偽の***ファイアウォール**を作成し、クラスター内外の直接通信をブロックしている。

長い間、ほとんどのサービスはクラスター内で提供できた（品質はともかく）が、クラスター外の他のクラスターと通信しなければならない要件が常に存在する。ことわざに「彼を知り己を知れば百戦殆うからず」とあるように、ファイアウォールがどのように構築されているかを深く理解してこそ、より良く克服できるのである。

## パート2 どのように構築するか？
もしあなたがこのクラスターの管理者なら、どのように壁を構築するだろうか？

### 2.1 IPブロッキング
クラスターのすべてのルーターを制御できるなら、最も直接的な方法はブラックリストにあるIPをブロックすることである。ルーターがデータパケットの宛先IPがブラックリストにあることを検出すると、ルーターはデータパケットを破棄するか、存在しない場所へ転送する。

この方法の核心は、大規模なブラックリストを維持する必要があることである。
- 特定のサーバー向けの単一IP
- コンピュータルーム全体のIPセグメントブロッキング、例えば一部の安価なVPSプロバイダーなど

### 2.2 DNS汚染
DNSクエリ（UDPバインドポート53）はデフォルトで暗号化されておらずコネクションレスであるため、これは傍受に大きな利便性を提供する。

これは非常に効果的で経済的な方法である。DNSは現代ネットワークの基盤であり、ほぼすべてのサービスにドメイン名が付与されており、サービスの正しいアクセスにはDNS解決が必要である。クラスター内のユーザーがDNSを使用して「違法な」サービスのドメイン名を解決しようとすると、クラスターのDNSサーバーは127.0.0.1などの誤った解決結果を返すだけでよい。こうして、ユーザーの「違法な」リクエストはネットワークカードから出ることさえない。

もちろん、この方法も比較的簡単に「対処」できる。ユーザーはローカルのhostsファイルを手動で修正し、正しいドメイン名と対応するIPアドレスを追加し、ローカルのhostsファイルがDNS解決に優先的に使用されるように設定するだけでよい。

### 2.3 キーワードフィルタリングとTCP RSTリセット
IPがブロックされていなくても、ユーザーのリクエストパケットに特定の「機密文字」が含まれている場合、*管理者*が行動を起こす。

これは非暗号化トラフィック（HTTPなど）または半暗号化トラフィック（TLSハンドシェイク段階など）に対する精密打撃である。管理者はデータパケットを抽出してプリセットの「機密」シソーラスに一致した場合、通信の両側（ユーザーのコンピューターとサーバー）に偽造メッセージを送信する。**RST**パケットは現在のTCP接続を強制的に中断させる。ウェブページの読み込み途中で突然*「Connection has been reset」*と表示されるのは、常にこのようなものである。

### 2.4 ディープパケットインスペクション
宛先ドメイン名とIPアドレスに基づいて傍受を実現できない場合、傍受すべきかどうかを判断するためにより深いデータ分析が必要である。現在ほとんどの通信はTLSで暗号化されているが、ディープパケットインスペクション（DPI）はデータパケットを透過して識別し傍受することができる。

DPI検出のほとんどは`L3`と`L7`を対象とし、送信元/宛先IPとリクエストペイロードを含む。DPIプロセス全体の流れは以下の通り：
1. 抽出：DPIエンジンがこのパッケージをキャプチャし、ポートを認識して対応するパースモジュールを呼び出す。`80`なので`HTTP`パースモジュールを呼び出す。またDPIは*フィンガープリント認識*でも検出できる。これはプロトコル固有のバイトシーケンスと長さ分布である
2. 再構成：検索語が非常に長く複数のパッケージに分割されている場合、DPIは*メモリ内でそれらを再構成*（TCP Reassembly）し、サブコントラクトによってキーワードが検出を逃れないようにする
3. マッチング：DPIはペイロードをスキャンして、プリセットのフィルタリングルールである*秘密キーワード*を検出する
4. アクション：パケットを破棄するか、傍受のために`TCP RST`パケットを送信する

これが、現代のトンネリングプロトコル（`VLESS`/`REALITY`など）が既知のシグネチャを排除し、すべてのハンドシェイクプロセスを完璧で欠陥のないHTTPSトラフィックとして偽装することに努める理由である。その目標は、DPIエンジンにこれが準拠サイトに送信された通常のデータパケットであると信じ込ませることである。

### 2.5 フロー統計分析
これは現在、対処が最も困難な動的方法である。この時点で、分析と検出はもはや静的なドメイン名/IP/キーワードに依存せず、トラフィックセグメント全体の行動特性に焦点を当てる。

しかし、どのようにトラフィックを分析するのか？最も明らかな側面の1つは、すべての暗号化トラフィックが高いランダム性を示すことである。IPが一貫して高エントロピーのランダムデータを出力し、典型的なHTTPSフィンガープリントを持たない場合、そのIPはフラグが立てられる。
同様に、接続時間とパケットサイズによっても特徴が明らかになる：
- プロキシトラフィックは通常、持続的な長期間接続である
- ビデオストリーミング、ウェブブラウジング、暗号化トンネルのパケット長特性は全く異なる

ユーザーのデータ行動が評価システムの特定の閾値を超えると、ブロックされる。

## パート3 どのようにトンネルを掘るか？
現在のネットワーク回避技術のエコシステムでは、`V2Ray`、`Xray`、`sing-box`が最も核心的で成熟した3つのフレームワークである。
- `V2Ray`：*多入力多出力*と*複雑なルーティング*の概念を導入。`VMess`暗号化プロトコルを先駆けて開発し、その*ルーティングエンジン*はドメイン名、IPアドレス、地理的位置など複数の次元に基づくトラフィック分散をサポートする。*トランスポート層難読化*を追加し、`WebSocket`、`mKCP`、`HTTP/2`、`QUIC`など複数の基盤トランスポート方式をサポートする。
- `XRay`：`V2Ray`からフォークされた強化版であり、現在コミュニティで最も人気のある選択肢である。`XTLS`統合に対してより急進的なアプローチを取る。
  - `VMess`：`VMess`の冗長な暗号化と検証を放棄し、これらのタスクを基盤のTLS層に委任することで、CPUオーバーヘッドが大幅に削減される。
  - `XTLS Vision/Reality`：パディングなどの方法を使用して、TLSトラフィックの長さフィンガープリンティングに対抗できる。正規のウェブサイトの証明書特性を「*窃取*」し、プロキシトラフィックの特性を大手企業の`HTTPS`トラフィックと同一にする。
- `sing-box`：Goで書かれているが、メモリ管理と並行性能において広範かつ深い最適化が行われている。
  - `全プロトコルサポート`：`VLESS`、`VMess`、`Trojan`に加えて、`Hysteria2`（修正された`QUIC`の一種）、`TUIC`、`WireGuard`をネイティブサポートする。
  - `カーネル統合`：優れた`TUN/TProxy`実装を採用。すべてのシステムトラフィックを引き継ぎ、ブラインドスポットのない透過プロキシを実現できる。
  - `rule-set`：プリコンパイルされたルールセットをサポートする。

|                     | `V2Ray` | `Xray` | `sing-box` |
| :-:                 | :-:     | :-:    | :-:        |
| ルーティング性能     | 中      | 高     | 最高       |
| 隠蔽性              | 高      | 最高   | 最高       |
| 透過プロキシ         | 中      | 高     | 最高       |

ここでは、現在利用可能な最も先進的で高度に隠蔽された`VLESS + XTLS + REALITY`ソリューションを使用してデプロイを行う。
```bash
# base environment
# Debian 12
# 1. install tools
apt update && apt upgrade -y
apt install curl wget unzip chrony -y

# ensure time sync
systemctl enable --now chrony

# disable firewall
systemctl disable firewalld

# 2. download bin files
mkdir -p /usr/local/bin/xray
mkdir -p /usr/local/etc/xray
wget https://github.com/XTLS/Xray-core/releases/latest/download/Xray-linux-64.zip
unzip Xray-linux-64.zip -d /usr/local/bin/xray
chmod +x /usr/local/bin/xray/xray

# 3. gen uuid and secret key
/usr/local/bin/xray/xray uuid
/usr/local/bin/xray/xray x25519
```

`config.json`のテンプレートがあり、`inbounds.settings.clients.id`を`uuid`に、`inbounds.streamSettings.realitySettings.privateKey`を`x25519 private key`に置き換える：
```json
{
  "log": {
    "loglevel": "warning"
  },
  "inbounds": [
    {
      "port": 443, 
      "protocol": "vless",
      "settings": {
        "clients": [
          {
            "id": "here put your uuid", 
            "flow": "xtls-rprx-vision"
          }
        ],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "tcp",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "dest": "www.lovelive-anime.jp:443", 
          "xver": 0,
          "serverNames": [
            "www.lovelive-anime.jp"
          ],
          "privateKey": "here put your private secret key", 
          "shortIds": [
            "0123456789abcdef" 
          ]
        }
      }
    }
  ],
  "outbounds": [
    {
      "protocol": "freedom",
      "tag": "direct"
    }
  ]
}
```

- `dest`：`TLS 1.3`と`H2`をサポートし、VPSに物理的に近い、大規模で評判の良い海外ウェブサイトを選択することを推奨する。
- `shortIds`：最大16文字の16進数文字（0-9、a-f）。

サーバーを起動：
```bash
/usr/local/bin/xray/xray run -config /usr/local/etc/xray/config.json

# expose port, this config.json server with 443
ufw allow 443/tcp
iptables -I INPUT -s 0.0.0.0/0 -p tcp --dport=443 -j ACCEPT
```

その後、`v2rayN`などのクライアントでサーバーに接続できる。
VMessサーバーを追加：
- addr: VPS IP
- port: Xray port(here is 443)
- user id: [uuid]
- protocol: tcp
- flow: xtls-rprx-vision
- TLS: reality
- SNI: [domain]
- PublicKey: [public key]
- ShortId: [shortId]

これでリアルワールドに接続するトンネルを掘ることができた！
